How it works

Seller fills the form | | POST { product_type, quantity, price_per_unit, city } v Supabase Edge Function (find-buyers) | | query: active needs matching this product v Supabase Postgres (businesses + buyer_needs) | | matching rows v Function scores each buyer 0-100 and sorts | | JSON response v HTML page draws the results table
POST /api/find-buyers

Live URL: https://<project-ref>.supabase.co/functions/v1/find-buyers

Takes the details of a product a seller wants to move, and returns businesses that are looking to buy it — scored and sorted, best match first.

How the match score is calculated

Every buyer starts at 40 points for selling the same product, then earns more:

ConditionPointsReason shown
Product type matches40Same product
price_per_unit ≤ max_price+25Price is within budget
quantity ≥ quantity_required+20Has enough quantity
Buyer is in the same city+15Same city

Maximum 100. Results are sorted highest first, and every score carries its reasons so the number is never unexplained.

Security

Browser --(anon key)--> Edge Function --(service role key)--> Database | | | cannot read does the locked by the database reading RLS directly on your behalf

Row Level Security is enabled on both tables, so the anon key cannot read them directly — even though it is visible in the page source. The Edge Function uses the service_role key, which stays on Supabase’s servers and never reaches the browser.

Why the anon key is safe to publish: it is an identifier, not a password. It only lets the browser call the function. RLS is what protects the data.
